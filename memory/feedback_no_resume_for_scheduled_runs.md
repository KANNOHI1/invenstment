---
name: 定期実行を固定セッションの --resume で回さない
description: 毎日の定型処理（巡回・監視）を 1 つのセッションに --resume で追記し続けると履歴が肥大し cache read が日ごとに膨らむ。定期実行は毎回新規セッションで起動し、文脈はファイルに置く（2026-09-18 投資プロジェクトで巡回・ニュース監視を廃止した根拠）
type: feedback
last_verified: 2026-09-18
---

**定型の定期処理（毎朝の巡回・毎日の監視など）を、固定セッション ID を `--resume` で使い回す形で運用しない。**

**Why**: 投資プロジェクトの巡回セッションで実測。1 ターンあたりの cache read が 9/11 256K → 9/14 405K → 9/18 612K トークン（8 日で 2.4 倍）、1 日の合計 7,000 万トークン。1M 上限に近づけば自動圧縮で過去の判断を失ったまま走る。固定セッションにしたのは「スマホの Remote Control スレッドで読める」「セッション内 cron が使える」の 2 点のためだったが、その便利さより肥大の害が大きいと菅野さんが判断し 2026-09-18 に廃止（「パトロールやめよう。随時監督に聞くわ」）。これは `~/.claude/CLAUDE.md` の「定型処理は独立セッション化する」に最初から書いてあった原則で、それに反した設計だった。

**How to apply**:
- 定期実行が要るなら **Task Scheduler / cron から毎回新規セッション**を起動する。必要な文脈は状態ファイル（例: `rotation_state.md` 冒頭ブロック・`thesis_register.md`）に置き、履歴で引き継がない
- セッション内 cron（CronCreate）は「セッションが生きている間だけ・7 日失効」の上に、この肥大を必ず伴う。**定期実行の主経路にしない**
- 固定セッションを使う場合でも、jsonl の `cache_read_input_tokens` の最終値を週 1 で見て 300K を超えたら切り替える
- 監視の手を減らしたときは「随時、監督に聞く」で足りるかを先に問う。自動化が目的化していないか
